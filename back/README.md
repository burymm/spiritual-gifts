# back — API сохранения профилей

Fastify + TypeScript. Профили (ответы анкеты + веса качеств) хранятся в
Postgres — сейчас это Supabase, позже можно переехать на VPS: схема и запросы
на обычном `pg`, без привязки к хостингу.

Входа в этой итерации нет. Профиль доступен по своему `id` — это UUID,
который служит ключом ссылки (`GET /api/profiles/<id>`). Кто знает ссылку,
тот может прочитать профиль; так устроено сохранение без регистрации.

## Запуск

```bash
cd back
npm install
cp .env.example .env    # вписать DATABASE_URL из Supabase
npm run dev             # http://localhost:3000
```

При старте сервер сам применяет недостающие миграции (файлы в `migrations/`,
каждый — в своей транзакции, повторный запуск безопасен). Отдельная команда:
`npm run migrate`.

Где взять `DATABASE_URL` для Supabase: проект → **Connect → Database →
Session pooler (URI)**. Формат (для проекта в регионе `eu-west-1`, порт session-пуллера 5432)

```
postgresql://postgres.<project-ref>:<password>@aws-0-eu-west-1.pooler.supabase.com:5432/postgres
```

Свой корневой сертификат Supabase (`Supabase Root 2021 CA`) отсутствует в системном
хранилище, поэтому для хостов `*.supabase.co` бэк сам добавляет `sslmode=no-verify`:
соединение шифруется, но цепочка не проверяется. Свой CA можно указать явно —
параметром `sslrootcert=` в той же строке, тогда подмена не сработает.

Схему в Supabase можно создать и через Dashboard (SQL Editor → вставить
`migrations/0001_create_profiles.sql`), но тогда таблица `schema_migrations`
не появится и миграции будут применяться повторно — безопасно, но лучше
дать бэку применить их самому.

## Маршруты

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/api/health` | 200 `{status:"ok",db:true}` или 503, если база не отвечает |
| `POST` | `/api/profiles` | Создать профиль → 201 с телом профиля |
| `GET` | `/api/profiles/:id` | Прочитать профиль → 200 / 404 |
| `PATCH` | `/api/profiles/:id` | Частично обновить → 200 / 404; итоговая запись проверяется целиком |
| `DELETE` | `/api/profiles/:id` | Удалить → 204 / 404 |

Тело `POST`:

```jsonc
{
  "title": "Мой профиль",        // необязательно, до 200 символов
  "answers": { "1": 4, "2": 2 }, // необязательно; id вопроса → ответ 1…5
  "weights": [50, 50, ...],      // обязательно: 24 целых, каждый 1…1176, сумма 1200
  "source": "survey"             // необязательно: uniform | survey | calibrated | aggregate
}
```

Ответы ошибок — JSON вида `{"error": "...", "issues": ["..."]}` с текстом на
русском; код 400 означает, что данные не прошли проверку, 404 — профиль или
маршрут не найден, 503 — база недоступна.

## Правила валидации

Зеркало движка фронта (`front/src/app/core/config.ts`):

- `QUALITY_COUNT = 24` — столько весов должно быть в профиле;
- `BASE_WEIGHT = 50` — пул `24 × 50 = 1200`, сумма весов ровно ему равна;
- вес целый, от 1 до `пул − число качеств` (1176);
- ответ целый, от 1 до 5, ключ — числовой id вопроса.

Значения переопределяются в `.env`, если фронт поменяет конфиг.

## Схема БД

`migrations/0001_create_profiles.sql` — таблица `profiles`:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | `uuid` PK | Идентификатор и ключ ссылки |
| `title` | `text` | Название профиля |
| `answers` | `jsonb` | `{"<id вопроса>": 1…5}` |
| `weights` | `jsonb` | Массив 24 целых весов, сумма 1200 |
| `source` | `text` | Откуда веса: uniform / survey / calibrated / aggregate |
| `created_at`, `updated_at` | `timestamptz` | Моменты создания и изменения |

Ограничения `check` в самом SQL страхуют запись от мусора; жёсткую проверку
пула делает приложение, потому что число качеств задано конфигом.
