# back — API сохранения профилей

Fastify + TypeScript. Профили (ответы анкеты + веса качеств) хранятся в
Postgres — сейчас это Supabase, позже можно переехать на VPS: схема и запросы
на обычном `pg`, без привязки к хостингу.

Вход — через Google OAuth, а на локальной сборке без ключей Google — эмуляция
входа почтой (режим `mock`, см. «Вход» ниже). Вход обязателен: все маршруты
профилей без токена отвечают 401, а профиль всегда принадлежит почте из
сессии. Профиль без владельца, оставшийся от версии без обязательного входа,
забирает первый вошедший, который его сохранит.

## Вход

Режим выбирается переменной `AUTH_MODE` (по умолчанию — `google`, если заполнены
`GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`, иначе `mock`):

- **google** — настоящий OAuth: `GET /api/auth/login` ведёт на согласие Google,
  `GET /api/auth/callback` меняет code на сессию (проверяется подпись ID-токена
  по ключам Google, аудитория и срок), дальше фронт получает токен в `#token=`.
  В Google Console укажите Redirect URI: `http://127.0.0.1:3000/api/auth/callback`
  (берётся из `API_PUBLIC_ORIGIN`).
- **mock** — эмуляция входа для локальной сборки: `POST /api/auth/mock` с почтой
  выдаёт токен, подписанный тем же секретом, дальше поведение неотличимо от
  настоящего входа. В режиме `google` этот маршрут отвечает 403.

Сессия — подписанный токен (`SESSION_SECRET`, без него генерируется случайный
на каждый запуск) в localStorage фронта; на каждый запрос он приходит заголовком
`Authorization: Bearer …`. Куки не используются: фронт и API на разных
origin'ах, а `SameSite` мешал бы. Токен несёт только почту и срок годности —
запросы к профилям сверяются с колонкой `owner_email`.

Что настроить в `back/.env` для настоящего входа: `AUTH_MODE=google`,
`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `SESSION_SECRET`,
`FRONT_ORIGIN` (откуда приходят запросы) и `API_PUBLIC_ORIGIN` (куда Google
возвращает).

## Запуск

```bash
cd back
npm install
cp .env.example .env    # вписать DATABASE_URL из Supabase
npm run dev             # http://localhost:3000
```

При старте сервер сам применяет недостающие миграции (файлы в `migrations/`,
каждый — в своей транзакции, повторный запуск безопасен). Отдельная команда:
`npm run migrate`.

Где взять `DATABASE_URL` для Supabase: проект → **Connect → Database →
Session pooler (URI)**. Формат (для проекта в регионе `eu-west-1`, порт session-пуллера 5432)

```
postgresql://postgres.<project-ref>:<password>@aws-0-eu-west-1.pooler.supabase.com:5432/postgres
```

Свой корневой сертификат Supabase (`Supabase Root 2021 CA`) отсутствует в системном
хранилище, поэтому для хостов `*.supabase.co` бэк сам добавляет `sslmode=no-verify`:
соединение шифруется, но цепочка не проверяется. Свой CA можно указать явно —
параметром `sslrootcert=` в той же строке, тогда подмена не сработает.

Схему в Supabase можно создать и через Dashboard (SQL Editor → вставить
`migrations/0001_create_profiles.sql`), но тогда таблица `schema_migrations`
не появится и миграции будут применяться повторно — безопасно, но лучше
дать бэку применить их самому.

## Маршруты

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/api/health` | 200 `{status:"ok",db:true}` или 503, если база не отвечает |
| `GET` | `/api/auth/config` | Режим входа: `{mode:"google"\|"mock"}` |
| `GET` | `/api/auth/login?origin=` | Редирект на согласие Google (400 для чужого origin или в mock) |
| `GET` | `/api/auth/callback` | Обмен code на сессию → 302 на фронт с `#token=` |
| `POST` | `/api/auth/mock` | Эмуляция входа: `{email}` → 201 `{token,email}` (только mock) |
| `GET` | `/api/auth/me` | `{email}` по токену / 401 без входа |
| `POST` | `/api/auth/logout` | 204 (токен выбрасывает клиент) |
| `POST` | `/api/profiles` | Создать профиль → 201; владелец — почта из токена, без токена — 401 |
| `GET` | `/api/profiles/mine` | Профиль вошедшего → 200 / 404, без токена — 401 |
| `GET` | `/api/profiles/:id` | Прочитать → 200 / 404; без токена — 401, чужой профиль — 404 |
| `PATCH` | `/api/profiles/:id` | Обновить → 200 / 404; без токена — 401; профиль без владельца «забирается» вошедшим |
| `DELETE` | `/api/profiles/:id` | Удалить → 204 / 404; без токена — 401 (только владелец) |

Тело `POST`:

```jsonc
{
  "title": "Мой профиль",        // необязательно, до 200 символов
  "answers": { "1": 4, "2": 2 }, // необязательно; id вопроса → ответ 1…5
  "weights": [50, 50, ...],      // обязательно: 24 целых, каждый 1…1176, сумма 1200
  "source": "survey"             // необязательно: uniform | survey | calibrated | aggregate
}
```

Ответы ошибок — JSON вида `{"error": "...", "issues": ["..."]}` с текстом на
русском; код 400 означает, что данные не прошли проверку, 401 — вход не
выполнен, 404 — профиль или маршрут не найдены, 403 — маршрут выключен в этом
режиме входа, 503 — база недоступна.

## Правила валидации

Зеркало движка фронта (`front/src/app/core/config.ts`):

- `QUALITY_COUNT = 24` — столько весов должно быть в профиле;
- `BASE_WEIGHT = 50` — пул `24 × 50 = 1200`, сумма весов ровно ему равна;
- вес целый, от 1 до `пул − число качеств` (1176);
- ответ целый, от 1 до 5, ключ — числовой id вопроса.

Значения переопределяются в `.env`, если фронт поменяет конфиг.

## Схема БД

`migrations/0001_create_profiles.sql` — таблица `profiles`:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | `uuid` PK | Идентификатор и ключ ссылки |
| `title` | `text` | Название профиля |
| `answers` | `jsonb` | `{"<id вопроса>": 1…5}` |
| `weights` | `jsonb` | Массив 24 целых весов, сумма 1200 |
| `source` | `text` | Откуда веса: uniform / survey / calibrated / aggregate |
| `owner_email` | `text` | Почта вошедшего; `null` — профиль от версии без обязательного входа |
| `created_at`, `updated_at` | `timestamptz` | Моменты создания и изменения |

`owner_email` добавляет миграция `0002_add_owner_email.sql` с индексом по почте
и времени обновления — он и даёт `GET /api/profiles/mine`.

Ограничения `check` в самом SQL страхуют запись от мусора; жёсткую проверку
пула делает приложение, потому что число качеств задано конфигом.
